    • IA-SYS-001
      1. Python package IA-SYS-001 The software SHALL be implemented as an installable Python package named ironair.

      All public APIs SHALL be importable using:

      import ironair
      from ironair import constants
      from ironair import chemistry
      from ironair import components
      from ironair import simulation
      from ironair import scenarios
      from ironair import plotting

      The implementation SHALL use a standard src/ package layout.

      The project SHALL provide editable installation using:

      pip install -e ".[dev,notebooks]"
    IA-REQ-001
    1. StrictDoc source of truth IA-REQ-001 All requirements SHALL be maintained in StrictDoc .sdoc files.

    Markdown SHALL be used for supplementary explanatory design documents but SHALL NOT
    replace the authoritative requirements database.
    IA-REQ-002
    2. Requirement identifiers IA-REQ-002 Each requirement SHALL possess a permanent unique ID.

    Required prefixes: IA-SYS, IA-REQ, IA-CON, IA-CHM, IA-FE, IA-HER, IA-ORR, IA-OER,
    IA-GDL, IA-ELY, IA-SEP, IA-COL, IA-CEL, IA-THM, IA-AIR, IA-FLD, IA-HEX, IA-STK,
    IA-MOD, IA-ENC, IA-DC, IA-CNV, IA-INV, IA-TRF, IA-GRD, IA-CTL, IA-EST, IA-DEG,
    IA-FLT, IA-ODE, IA-NBK, IA-PLT, IA-TST, IA-DOC.
    IA-REQ-003
    3. Function-level traceability IA-REQ-003 Every public physics, control, solver, plotting, and scenario function SHALL contain a
    StrictDoc @relation marker.

    A function implementing several requirements SHALL contain separate relation markers
    for every applicable requirement.

    Internal helper functions SHALL be traceable to the applicable implementation requirements.

    The traceability system SHALL identify Requirement -> Python Function -> Test -> Notebook Scenario.
    IA-REQ-004
    4. Bidirectional traceability IA-REQ-004 CI SHALL verify that every implementation requirement has an associated function,
    every required function exists, every required function is covered by tests,
    every documented scenario has a notebook, every required notebook executes successfully,
    all source-level requirement references resolve to valid StrictDoc UIDs, and every
    requirements-to-source reference identifies an existing Python source element.
    • IA-TD-006
      6. Traceability test IA-TD-006 Parse reqs/**/*.sdoc UIDs and src/**/*.py @relation markers.
    IA-REQ-005
    5. Requirement verification IA-REQ-005 Every physical requirement SHALL specify acceptance criteria that can be objectively tested.

    Compliance SHALL be verified through unit tests, integration tests, conservation checks,
    numerical convergence tests, and documented model validation.

    Passing software tests SHALL NOT be represented as physical validation against experimental hardware.
    IA-CON-001
    6. Constants module IA-CON-001 Implement src/ironair/constants.py providing F_C_MOL, R_J_MOL_K, T_REF_K, P_REF_PA,
    M_FE_KG_MOL, M_O2_KG_MOL, M_H2O_KG_MOL, and M_KOH_KG_MOL.

    Fundamental constants SHALL be immutable.
    • IA-TD-002
      2. Constants immutability test IA-TD-002 Read F_C_MOL, R_J_MOL_K, T_REF_K, P_REF_PA, M_FE_KG_MOL, M_O2_KG_MOL, M_H2O_KG_MOL,
      and M_KOH_KG_MOL. Attempting assignment shall fail.
    IA-CON-002
    7. Parameter definitions IA-CON-002 Every component SHALL use explicit, typed parameter objects.

    Parameters SHALL include name, value, SI unit, physical meaning, valid range,
    source classification, literature reference when available, uncertainty when available,
    and calibration status.

    Parameter categories SHALL distinguish fundamental constant, literature value,
    experimental measurement, engineering design assumption, calibrated coefficient,
    and unverified placeholder.
    IA-CON-003
    8. Property models IA-CON-003 Implement concentration- and temperature-dependent properties for KOH conductivity,
    KOH density, KOH viscosity, KOH heat capacity, KOH water activity, dissolved oxygen
    solubility, oxygen diffusivity, gas-phase diffusivity, iron conductivity, thermal
    conductivity, reaction rate constants, and electrochemical exchange-current densities.

    Property models SHALL enforce their valid domains.
    • IA-SYS-002
      2. Integrated physics simulation IA-SYS-002 The software SHALL model the complete iron-air battery as a coupled multiphysics system.

      The model SHALL include metallic iron electrode, iron hydroxide and oxide phases,
      oxygen reduction electrode, oxygen evolution electrode, hydrogen evolution, alkaline
      electrolyte, electrolyte transport, separator, gas diffusion layer, current collectors,
      cell assembly, thermal system, air intake, fan/blower, gas manifolds, ventilation,
      electrolyte reservoir, circulation pump, piping, valves, heat exchanger, battery stack,
      battery module, battery enclosure, DC electrical distribution, DC/DC conversion, grid
      inverter, transformer, grid interface, measurement sensors, battery management,
      supervisory control, fault management, state estimation, and degradation and aging.

      These components SHALL interact through shared physical quantities and conserved
      material, charge, and energy flows.
    IA-CHM-001
    9. Stoichiometric reaction network IA-CHM-001 Implement a common chemical reaction network.

    Mathematical model:

    dn/dt = S @ r + B @ q

    Where S is the chemical stoichiometric matrix, r is the reaction-rate vector,
    B maps boundary flows to species inventories, and q is the boundary-flow vector.

    The reaction network SHALL enforce elemental conservation.
    IA-CHM-002
    10. Iron conversion IA-CHM-002 Implement Fe + 2OH- <-> Fe(OH)2 + 2e-.

    Calculate reaction rates from electrode kinetics and Faraday's law.
    IA-CHM-003
    11. Magnetite formation IA-CHM-003 Implement configurable conversion between iron hydroxide and magnetite, including
    electron transfer and correct stoichiometry.
    IA-CHM-004
    12. Oxygen reduction reaction IA-CHM-004 Implement O2 + 2H2O + 4e- -> 4OH-.
    IA-CHM-005
    13. Oxygen evolution reaction IA-CHM-005 Implement 4OH- -> O2 + 2H2O + 4e-.
    IA-CHM-006
    14. Hydrogen evolution reaction IA-CHM-006 Implement 2H2O + 2e- -> H2 + 2OH-.
    IA-CHM-007
    15. Butler-Volmer kinetics IA-CHM-007 Implement nonlinear electrode kinetics with exchange-current density, transfer coefficients,
    local overpotential, temperature, species activities, electrode surface area, and
    reaction availability.
    • IA-TD-004
      4. Butler-Volmer equilibrium test IA-TD-004 Evaluate electrode current at zero overpotential with finite activities.
    IA-CHM-008
    16. Nernst potentials IA-CHM-008 Calculate equilibrium potentials using thermodynamically consistent activities and
    standard electrode-potential references.
    IA-CHM-009
    17. Reaction thermodynamics IA-CHM-009 Calculate Gibbs free energy, reaction enthalpy, reaction entropy, equilibrium cell
    potential, reversible reaction heat, and irreversible reaction heat.
    IA-CHM-010
    18. Chemistry conservation IA-CHM-010 The central chemistry module SHALL check iron atom conservation, oxygen atom conservation,
    hydrogen atom conservation, potassium conservation, carbon conservation, charge balance,
    electron transfer, and reaction stoichiometry.
    • IA-TST-001
      32. Elemental conservation IA-TST-001 The stoichiometric network SHALL conserve chemical elements for every reaction.
      • IA-TD-003
        3. Elemental conservation test IA-TD-003 For each column of S, compute the elemental residual E @ S[:, j].
    • IA-SYS-003
      3. ODE-based components IA-SYS-003 Every physical component SHALL expose a dynamic ODE model.

      Each component SHALL explicitly define: state vector, state units, initial conditions,
      input variables, output variables, governing differential equations, algebraic constitutive
      relations, physical parameters, boundary conditions, conservation residuals, numerical
      constraints, and associated StrictDoc requirement IDs.

      Every component SHALL provide a rhs() method returning state derivatives.

      The generic mathematical representation SHALL be:

      dx/dt = f(t, x, inputs, parameters)

      Where required:

      0 = g(t, x, algebraic_variables, inputs, parameters)

      Algebraic variables SHALL be solved consistently during RHS evaluation or through a
      supported DAE backend.

      An artificial time constant SHALL NOT be introduced solely to make an instantaneous
      physical relation appear dynamic.

      Passive structures, such as current collectors, SHALL possess actual dynamic states
      where justified, such as temperature. Their instantaneous electrical resistance SHALL
      remain an algebraic relation.
    IA-ODE-001
    19. Common component protocol IA-ODE-001 Every dynamic component SHALL implement rhs(self, t, y, inputs, context).

    The RHS SHALL be deterministic for a fixed state, time, input, and parameter configuration.

    It SHALL NOT modify component state through hidden side effects.
    • IA-IRS-002
      2. RHS signature IA-IRS-002 Every dynamic component SHALL expose:

      def rhs(self, t, y, inputs, context) -> numpy.ndarray

      t is time in seconds, y is a 1-D float64 state vector, inputs is a mapping of named
      physical inputs, and context carries shared couplings without hidden mutation of
      component parameters.
    • IA-SDD-002
      2. Dynamic component base IA-SDD-002 All physical components SHALL implement ironair.ode.protocol.DynamicComponentProtocol
      and MAY inherit ironair.ode.component.DynamicComponent for shared validation.

      rhs(t, y, inputs, context) SHALL be a pure function of its arguments for a fixed
      parameter configuration.
    • IA-TD-005
      5. RHS determinism test IA-TD-005 Evaluate rhs twice with identical arguments.
    IA-ODE-002
    20. State definitions IA-ODE-002 Each component SHALL publish named state metadata and a validated state vector layout.

    State arrays SHALL be NumPy arrays.
    IA-ODE-003
    21. Coupled solver IA-ODE-003 Implement ironair.simulation.CoupledSystem.

    The solver SHALL assemble component states into one global state vector, maintain a
    state-index map, resolve shared inputs and algebraic couplings, evaluate the coupled
    RHS, pass the assembled system to SciPy, detect numerical failures, and return state
    trajectories and diagnostics.
    • IA-IRS-003
      3. CoupledSystem simulate interface IA-IRS-003 ironair.simulation.CoupledSystem.simulate SHALL accept t_span, optional t_eval,
      optional inputs callable, solver method, and tolerances, and SHALL return a
      SimulationResult.
    IA-ODE-004
    22. Stiff solvers IA-ODE-004 The default integrated system SHALL use a stiff-capable solver, normally SciPy BDF or Radau.

    Nonstiff component demonstrations MAY use RK45 or DOP853.
    IA-ODE-005
    23. Numerical robustness IA-ODE-005 The simulation SHALL include state-specific absolute tolerances, relative tolerances,
    Jacobian sparsity, event detection, hybrid mode transitions, nonnegative inventory
    checks, solver diagnostics, and energy and mass conservation residuals.
    IA-ODE-006
    24. Multiscale execution IA-ODE-006 The system SHALL support millisecond, second, minute, hour, and multi-day simulation windows.

    Detailed electrochemical dynamics and long-duration grid dispatch SHALL be able to use
    different model fidelity settings while sharing the same physical parameter definitions.
    IA-NBK-001
    25. Notebook development environment IA-NBK-001 All notebooks SHALL be located in notebooks/.

    All notebooks SHALL import numerical models from the installed ironair package.

    No notebook SHALL contain a separate replacement implementation of a battery physics model.
    IA-NBK-002
    26. Seaborn visualization IA-NBK-002 All scenario notebooks SHALL use seaborn for the principal plots.

    Matplotlib MAY be used for figure management, multi-axis plots, annotations, and
    specialized graphics.

    Plots SHALL include title, axis labels, physical units, legend where necessary,
    scenario identifier, and physical operating assumptions.
    • IA-PLT-001
      31. Plot styling contract IA-PLT-001 Shared plotting functions SHALL apply a consistent seaborn theme and include physical units
      on labeled axes.
    IA-NBK-003
    27. Shared plotting API IA-NBK-003 Implement reusable plotting functions under ironair.plotting.

    Plotting functions SHALL accept structured simulation results or pandas DataFrames.
    • IA-IRS-004
      4. Plotting input types IA-IRS-004 ironair.plotting functions SHALL accept SimulationResult or pandas.DataFrame.
    IA-NBK-004
    28. Chemical model demonstrations IA-NBK-004 Immediately after implementing the baseline chemistry, create notebooks demonstrating
    iron oxidation, iron reduction, iron phase inventories, Butler-Volmer kinetics,
    Nernst potential, ORR kinetics, OER kinetics, hydrogen evolution, oxygen limitation,
    KOH conductivity, electrolyte concentration, reaction heat, and mass and charge conservation.

    Each notebook SHALL call the actual associated Python component.

    29. Component demonstrations IA-NBK-005 Every component SHALL have a notebook or explicitly designated notebook section containing
    component configuration, initial conditions, input stimulus, simulation execution,
    time-domain plots, parameter sensitivity, conservation or physical validation results,
    and discussion of observed behavior.
    IA-NBK-006
    30. Full-system scenario demonstrations IA-NBK-006 The notebook suite SHALL cover all required operating scenarios described in Section 9.

    IA-TST-002
    33. Charge conservation IA-TST-002 Electrode currents, capacitive currents, and reaction rates SHALL obey conservation of charge.
    IA-TST-003
    34. Energy conservation IA-TST-003 The coupled system SHALL account for electrical, chemical, thermal, and material-flow energy.
    IA-TST-004
    35. Physical state validity IA-TST-004 The simulation SHALL reject or explicitly report invalid physical states including negative
    species inventory, nonphysical porosity, invalid electrolyte volume, nonphysical absolute
    temperature, invalid pressure, impossible oxygen consumption, and nonphysical cell voltage
    or current conditions.
    IA-TST-005
    36. Numerical convergence IA-TST-005 The system SHALL include solver tolerance refinement tests and, for spatial models,
    mesh refinement tests.
    IA-TST-006
    37. Model validation tracking IA-TST-006 Software verification SHALL be distinguished from model validation.

    Experimental calibration and independent physical validation SHALL be separately tracked.
    • IA-TP-002
      2. Verification versus validation IA-TP-002 Automated tests verify software against the SDRS. They SHALL NOT be labeled as
      experimental hardware validation.
    IA-TST-007
    38. Automated unit tests IA-TST-007 Every exported physical calculation and dynamic component SHALL have automated pytest coverage.
    • IA-TP-001
      1. Phase-gate testing IA-TP-001 Each development phase SHALL have a passing pytest suite before the phase is complete.

      Phase 1: package import, constants, parameters, ODE protocol, StrictDoc UIDs.
      Phase 2: stoichiometric conservation, Butler-Volmer, Nernst, thermodynamics.
      Phase 3: chemistry notebooks execute.
      Phase 4+: component, coupled, scenario, and conservation tests as implemented.
    IA-TST-008
    39. Component integration tests IA-TST-008 Every coupled component interface SHALL have integration tests verifying dimensions,
    units, and conservation.
    IA-TST-009
    40. Notebook execution tests IA-TST-009 Every mandatory notebook SHALL execute from a clean kernel without manual intervention.
    IA-TST-010
    41. Requirements coverage gate IA-TST-010 CI SHALL fail when a required UID is missing, a requirement has no implementation function,
    a required function is missing, a required equation is not tested, a notebook references
    an unavailable API, a mandatory notebook fails execution, or conservation acceptance
    criteria fail.
    • IA-TP-003
      3. CI quality gates IA-TP-003 CI SHALL run ruff, mypy, pytest with coverage, StrictDoc validation, and

    IA-TST-011
    42. Reproducibility IA-TST-011 The simulation SHALL support deterministic parameter sets, recorded software versions,
    and fixed random seeds.
